## 8. SIGSEGV at end of session: ROOT-CAUSED
- **Regression: yes.** Culprit **1b69af8587** "perf(StatusQ): build only the chosen orientation's section layout".
- **Symbolized** (e2 kit libs, build IDs match the crash): `QQuickLayout::updatePolish → ensureLayoutItemsUpdated → setImplicitSize → QQuickItemPrivate::implicitWidthChanged → notifyChangeListeners → setImplicitWidth (qquickitem.cpp:7696) → doActivate → QSlotObjectBase::call (a lambda slot) → QQuickItem::setImplicitWidth (qquickitem.cpp:7714, virtual geometryChange) → bad pc`. I.e. a lambda connected to some item's `implicitWidthChanged` calls `setImplicitWidth` on a **freed** item.
- **The lambda is Qt's** `QQuickLayoutItemProxy::setTarget` (qtdeclarative 6.11.0 src/quicklayouts/qquicklayoutitemproxy.cpp:289-295): `connect(newTarget, &QQuickItem::implicitWidthChanged, fnBindImplW)` with **no context object**, lambda captures the proxy `this`. Neither `~QQuickLayoutItemProxy` nor `setTarget` disconnects it. Destroying a proxy while its target lives leaves a dangling slot (only connected when the target has a `Layout.*` attached object). Upstream dev already passes `this` as context (fixed there; 6.11.0 kit is not).
- **Why it now happens:** master builds both StatusSectionLayoutPortrait and ...Landscape once and never destroys them while the section lives. 1b69af8587 puts each behind `Loader { visible: false; active: visible }` (ui/StatusQ/src/StatusQ/Layout/StatusSectionLayout.qml, landscapeLoader/portraitLoader). `visible` read in a binding is the **effective** visibility, so the view is destroyed not only on rotation but **every time the section is hidden** (AppMain's `StackLayout { id: appView }` hides non-current sections), and rebuilt on return. Each view has LayoutItemProxy's with section-owned targets that survive: `headerContent`, `headerBackground`, `footer`, `rightPanelHeaderContent` (StatusSectionLayoutPortrait.qml:366-416, StatusSectionLayoutLandscape.qml:309-345). Every section switch adds 2 dangling lambdas per such target; the next implicit-size change of that target (layout polish) calls into freed memory. Crashes only when the freed slot was not reused by a live object → intermittent, grows with the session length (matches "end of session").
- **Desktop repro** (Qt 6.11.0 macOS, `qml`, MallocScribble): triage/repro/proxy_uaf.qml (Loader{active: visible} in a StackLayout page, LayoutItemProxy → section-owned ColumnLayout with Layout.fillWidth, toggle page + change panel size): SIGSEGV (exit 139) in 2/6 runs; same file with `active: true` (master-like): 0/4.
- **Fix options:**
  1. **Patch the e2 Qt kit** (backport upstream: pass `this` as context in both connects; also disconnect old target in setTarget). Fixes the class of bug app-wide (ChatInfoPanel, InlineSelectorPanel, SettingsContentBase, CommunitiesPortalLayout, ChangePasswordView use LayoutItemProxy too). Cost: kit rebuild of QtQuickLayouts only; memory 0; risk low. Does not help builds on stock Qt (desktop/iOS CI) → combine with 2 or 3.
  2. **Don't destroy the views on section hide**: `active` latched (`active: visible || item !== null`… i.e. keep once built) or bound to the chosen orientation (`root.chosenLayout === portraitLoader`) instead of effective visibility. Removes the per-switch rebuild (also a CPU cost on every section re-entry, see #4) and leaves destruction only on rotation (rare, still UAF-prone without 1/3). Memory: same savings as now for non-rotating phones (one orientation built); +the other view after a rotation if latched. Risk low.
  3. **Stop using LayoutItemProxy for section-owned targets in the two views** (use SectionPanelSlot, already used for the panels, or a plain parent/anchor slot for header/footer). Fixes on any Qt; medium effort, needs the layout tests re-run. Memory ≈0.
  Recommendation: 2 (bind to chosen orientation, not effective visibility) + 1 in the kit; 3 if the fix must hold on stock Qt.
